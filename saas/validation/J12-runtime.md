# Accès PostgreSQL temporaire de validation J12-2

À utiliser lorsque la préparation des accès est autorisée. Les comptes Auth A et B ont leurs propres mots de passe.

1. Sur votre PC Windows privé, désactivez l’historique et la synchronisation du presse-papiers avant de copier une valeur sensible. Ouvrez le projet Supabase `daxenvo-dev` (référence `mniconjzkvvvwqoxtzwu`), puis Vault. Ouvrez PowerShell dans le dépôt à jour sur la branche `feature/j12-ai-integration`. GitHub CLI doit être connecté avec un compte autorisé à écrire les secrets Actions du dépôt.
2. Exécutez `& .\saas\validation\prepare-j12-runtime.ps1` une seule fois. Ce script génère 32 octets aléatoires, les représente par 64 caractères hexadécimaux et construit la chaîne du Session Pooler à partir de cette même valeur. Il enregistre la chaîne dans le secret GitHub Actions `J12_RUNTIME_DSN` par entrée standard. Il copie uniquement le mot de passe dans le presse-papiers.
3. Collez immédiatement dans le champ **valeur** du secret Vault `J12_RUNTIME_PASSWORD`. Enregistrez, puis appuyez sur Entrée dans PowerShell pour libérer le presse-papiers. En cas d’interruption, videz-le. Une deuxième exécution génère un autre mot de passe et nécessite de remplacer les deux valeurs.
4. Une fois votre confirmation reçue, l’opérateur provisionne le rôle temporaire dédié depuis la valeur Vault et lui accorde uniquement le rôle applicatif prévu. Il vérifie la référence du projet, la durée de validité et les droits du rôle. Le DSN est réservé à GitHub Actions.
5. L’opérateur déclenche le prétest seul par un commit sur le marqueur `.github/j12-history-preflight` de la branche J12. Ce job reçoit uniquement le DSN et vérifie la connexion, le certificat et le nom du pooler, le chiffrement du segment PostgreSQL, l’identité du rôle et le passage au rôle applicatif. La transaction est en lecture seule. Un échec arrête la procédure avant les tests métier.
6. La campagne complète possède un marqueur distinct, `.github/j12-history-run`. Son job métier dépend d’un prétest réussi dans la même exécution. Les secrets Auth ne sont nécessaires que pour la campagne. En fin de validation, révoquer le rôle temporaire et supprimer les secrets de test et les seules données de campagne.
